# Proposal — Recorded response evidence, frozen activity views, and accepted-finding intake

Repository: `tkstang/skills`. Source baseline: `97029c25bacbc19669a5a9972e97c9ff320d44b1`. Beacon comparison: `Asymptote-Labs/agent-beacon` at `99c709081ad49da1c5ade205929b61b19360ed9b`. This proposal defines three bounded improvements to the existing session workflows. Implementation and enablement require their own authorized phase.

Provisional implementation estimates approved for planning: A **L**, B **combined M**, C **M**; reviewed first-slice sizing remains A **M conditional**, B **combined M**, C **S**. The section headings and sizing rationale below describe those bounded slices. The provisional budgets do not expand scope or authorize implementation, enablement or live acceptance.

## Existing contract and reason to act

Session Retro reviews a different session from a frozen sanitized narrative and sensitive complete activity JSON, with exact target identity, pairing checks, hashes and evidence cutoff. Current source is comparison context, never proof of the target's executed revision. Preserve the seven activity coverage states and the observation/interpretation/proposal split. [Freeze rules][retro-freeze]; [coverage and read-only boundaries][retro-boundaries]. The existing capture envelope carries versions, identity evidence, record counts, narrative locators and activity; narrative and atomic activity writes remain separate operations, so a partial pair is a capture failure. [Envelope][envelope]; [writes][writes].

Beacon distinguishes file digests from skill-name hashes, uses explicit omission markers in bounded evaluator input, and carries candidate/memory provenance into generated skills. These are useful reference patterns, with limits: scheduled inventory is not invocation evidence; head/tail selection is weaker than this repository's failure-priority projection; lineage does not authorize installation. [File digest][beacon-inventory]; [inventory timing][beacon-heartbeat]; [name hash][beacon-name]; [head/tail context][beacon-projection]; [lineage][beacon-promotion]; [direct install boundary][beacon-install]. Adopt only the useful distinctions; require no Beacon service, evaluator, installation, memory database or cross-repository dependency.

## A. Recorded native response evidence — M

Trigger: an operator asks which skill response content was recorded for a particular structured read in a reviewed session. The first useful slice qualifies one Codex carrier, computes its digest while exporting the existing decoded records, freezes the evidence in the existing capture envelope, and renders its basis and limitations in Retro. No separate collector or enablement hook is needed for this slice. Qualification runs first. If no runtime version that a concrete retrospective needs emits the structured carrier, record the gap and stop: no extraction, envelope bump or render. Support limited to historical versions requires a named retrospective need. Shell-command reads remain unattributed and never receive a skill digest. A negative qualification outcome is S or no implementation; M applies only after a useful carrier qualifies.

Codex source recognizes the historical `read_file` + `file_path` skill-read carrier and separately retains `function_call_output.payload.output` as a result with `call_id`. That demonstrates a carrier path, not that every Codex version records a complete skill body. [Carrier][codex-carrier]; [recognition fixture][codex-skill-fixture]. Before claiming support, qualify the combined path with a sanitized, representative per-runtime/version fixture showing a structured skill read, its recorded text result, exact correlation and truncation/decorations. Codex is first; Claude Code loaded-body injection is not established and is not a dependency. Cursor's current supported surface records calls without results, so it cannot supply response content on this path. [Runtime limits][retro-boundaries].

The hash domain is **recorded UTF-8 response bytes after documented extraction**, not raw file bytes. For the initial qualified Codex string carrier: take the JSON-decoded `payload.output` string from the exactly correlated native result and encode that string as UTF-8 without trimming, line-ending normalization, Unicode normalization, wrapper stripping, line-number removal or redaction. Reject malformed text encoding and unsupported non-string shapes with an unavailable diagnostic. Document the extraction rule and carrier qualification with the envelope contract. Compute before activity preview clipping; do not hash an export-rendered preview as if it were the original response. A historical artifact with only a preview cannot acquire missing response evidence later. No retrospective live-file or native-store reread may fill that gap.

Add only `evidenceBasis: native-recorded-content`, `status`, and an optional algorithm-tagged `digest` (`sha256:<64 lowercase hex>`), attached to the existing skill/resource reference and event/result locators. The existing envelope versions identify the extraction contract; do not introduce another observation ID, phase schema or resource registry. Status distinguishes a qualified recorded response from partial, unknown and unavailable evidence, independently of activity coverage. Any truncation/range limit, native decoration, or uncertain completeness keeps the skill-content claim partial or unknown; a digest can still identify the exact recorded response but cannot upgrade it to a complete skill file. Ambiguous call/resource association must not attach a digest to a skill. Preserve the original source locator and correlation evidence.

A response digest proves neither a raw `SKILL.md` revision nor executed runtime/supporting-resource bytes, model consumption, compliance or causality. Declared SemVer and Git revision remain separate comparison facts. The concrete consumer is **BL-260919-skill-evaluation-retro — Skill evaluation retro: activation, adherence, outcome, efficiency**: its version assessment may use qualified recorded response evidence instead of inference where available, while unknown executed revision remains unknown. Its implementation should align its existing inference-only criterion accordingly; this proposal does not silently change that item's text. [Evaluation][evaluation].

Keep evidence private with the existing frozen pair and authorized report lifetime; do not duplicate response bodies or publish paths/digests by default. Defer file/config collectors, realpath/symlink machinery, supporting-resource manifests and wider observation fields. Reconsider a narrowly authorized collector only for a documented runtime with no usable native carrier and a concrete retrospective blocked by that gap. M covers one qualified carrier, export/freeze/render integration and truthful fallback, not guaranteed cross-runtime capture.

## B. Frozen activity views — combined M amendment

Extend **BL-260919-grouped-activity-summaries — Grouped activity summaries and derived enrichments adapted from cli-continues** with unchanged ID/title. The combined item stays M only with a frozen-input reader and bounded view as its first slice, followed by the existing cli-continues enrichment work as a later slice. Both slices retain the item's recorded-recurring-need gate; a proposal alone does not satisfy that gate. Re-estimate when the enrichment slice starts or if both slices must ship together. [Existing scope][grouped].

Trigger: “Show the sequence between these record indexes or event keys in this frozen capture.” Read one explicitly supplied `StructuredActivityCapture`, select the bounded range from its `activity`, and render one `ActivityReport`-shaped view through the existing projection semantics. This first slice must be usable from a documented `session-retro` step end to end, without enriching tools, recapturing or scanning native stores. Validate supported envelope/activity versions and selectors before rendering. When narrative anchors are requested, verify the paired narrative; an activity-only view states its narrower input.

Reuse `deliveryRange`, `counts.capturedSource`, `counts.deliveredRange`, `counts.displayed`, `omitted` (including invocation/byte-limit groups), `callContexts` with `availability: outside-delivered-range`, coverage, diagnostics and source metadata. Add only `inputDigest` and `selection`; define `inputDigest` as SHA-256 over the exact supplied frozen capture file bytes. Selection records either half-open record-index bounds `[start, end)` in the capture's declared index base, or endpoint event keys resolved to the enclosing half-open record range. For event-key selection, include all events in both endpoint records and report the resolved bounds explicitly. Invalid, reversed, absent or ambiguous endpoints fail visibly. Keep displayed keys/locators unchanged. No `EpisodeView` type or separate projection-version field. [Existing report shape][activity-report]; [chronology and failure priority][projection-priority]; [range/limit validation][projection-validation]; [half-open range contract][projection-range].

Preserve recorded correlation and label context outside the selected range without counting it as selected events. Bound input bytes/events, selection width and output budgets. Retain captured/selected/displayed distinctions through existing count fields and explicit omissions; preserve already-recorded preview truncation and coverage. A view cannot restore content omitted from its frozen input. Reserve mandatory provenance/coverage/limit metadata; fail visibly if it cannot fit. A late failure must be displayed or accounted for as omitted. Payloads remain inert sensitive data. The frozen pair stays unchanged and authoritative.

No parser, discovery service, child/sidecar following, multi-source merge or task/causal inference is added. **BL-260919-read-linked-session-sidecars — Read linked session sidecars in the activity view** and **BL-260619-shared-session-log-substrate — Stateless multi-session activity merge** retain their own scopes. Existing Session Search remains discovery. These and A are optional composition, not prerequisites. [Sidecars][sidecars]; [merge][merge]; [search][search].

## C. Accepted finding intake — S

Trigger: after Retro ends, the user accepts a specific report-local finding and separately authorizes `author-skill` to prepare a proposal for its canonical owner. Acceptance is a decision to consider follow-up, not permission to edit a skill, install, publish, append a ledger or create memory. Retro remains read-only with only its expressly authorized report output exception. [Follow-through][retro-boundaries].

The smallest useful slice ships report-local finding IDs and a short `author-skill` intake together. Retain the existing Observed evidence, Interpretation, Likely cause, Owner, Proposed change and Validation fields. Assign stable IDs such as `F-001` within the finalized report; never silently renumber or reuse an ID within that report revision. [Existing fields][report-fields]. Compute SHA-256 over the **exact final UTF-8 report bytes** and emit an **external receipt**, in the response or at an explicitly authorized companion destination. The report does not contain its own digest. Finish rendering before hashing; when saving is authorized, hash the final saved file rather than a pre-save rendering; any byte change invalidates the receipt and requires a fresh receipt and renewed acceptance of the changed report. Verifiable later intake expects a report saved at an authorized destination. A response-only receipt is valid only for byte-exact same-session intake; otherwise follow the Stale case. This avoids self-reference without introducing a transfer store.

`author-skill` intake takes the report, finding ID, external receipt and the user's explicit follow-up scope/destination. Verify the final-byte digest, locate the exact finding, preserve its uncertainty and confirm its canonical owner. Then read the current owner baseline and existing proposals: produce a minimal sanitized proposal within that authority, request revalidation if the finding has gone stale, or conclude `no change`. Record the report digest and finding ID in authorized private proposal context; publish only redacted rationale and canonical repo-relative paths. Do not invent opaque handles or a private evidence service. The existing author workflow already owns contract, side effects and canonical placement. [Author contract][author-intake]; [prose and validation guidance][author-prose]; [source/version/build rules][owners].

Worked intake examples (synthetic, no session data):

1. **Accepted:** The user accepts `F-001` in final `report.md` and explicitly authorizes a proposal at a named destination for its canonical skill owner. The external receipt matches the report bytes and the current owner still has the reported gap. `author-skill` prepares only that scoped proposal, retaining the digest/finding ID in authorized private context. It does not edit or install the skill.
2. **Stale:** The report was edited after the external receipt was issued. Digest verification fails; no proposal is saved until a new receipt and renewed acceptance identify the changed report. If the receipt still matches but the current owner baseline changed materially, request revalidation of the finding before preparing a proposal. Neither case silently reuses the old approval.
3. **No change:** The receipt and accepted `F-001` match, and the user authorizes the same scoped proposal preparation, but the current owner already addresses the gap. Return `no change` with the current-base rationale. Do not invent a patch or append a ledger entry.

**BL-260919-retro-findings-ledger — Retro findings ledger with recurrence detection** remains a separate any-findings recurrence store; C follows only accepted findings into proposals and requires no ledger. Replace the ledger's Retro-append criterion with a separately and explicitly authorized **post-retro intake**. Configuration alone never grants append permission, even when the location is preconfigured. Retro never appends under an expanded report-output exception. A ledger entry records any finding and its limits, not necessarily an acceptance; recurrence is not permission to change a skill. Publish the exact ledger amendment with C. [Ledger][ledger].

Defer `AcceptedFindingRef`, private handle storage, transfer persistence, dedup/concurrency machinery and automated consumers until a real consumer requires a separately scoped contract. C needs no A/B delivery; A can improve evidence confidence and B navigation. `session-retro` and `author-skill` source versions, generated outputs and changelog must follow the existing authoring contract when this instruction/template slice is implemented. S reflects prose/template integration and manual examples, not a new runtime or store.

## Delivery and validation

A: qualify the Codex carrier, export its recorded-response digest into a versioned frozen capture and render its limitations in one vertical slice. Future automated checks belong at the export/extraction boundary: a known UTF-8 response digest, partial/decorated results and ambiguous association must not overclaim; unsupported carrier/envelope shapes must remain unavailable. Inspect existing extraction/export suites before adding coverage, and do not duplicate pair-write or generic projection checks.

B: deliver the frozen reader plus selector and bounded view together under recurring need. New automated coverage is limited to the reader boundary: unsupported envelope version, invalid selector, a selected result whose call lies outside the range, and mandatory metadata budget exhaustion. Existing projection tests remain responsible for generic determinism, failure priority and clipping. Later cli-continues ports retain attribution and defect-correction requirements.

C: deliver stable finding IDs, external final-byte receipt and author intake together, using accepted/stale/no-change manual examples. Keep Retro read-only. No prose snapshots, new store tests or live-provider calls are required for this slice. No unit depends on another repository shipping. Compatibility wrappers, background services and automatic promotion are outside these units.
