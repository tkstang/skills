### Medium

- **M1: Resolve the bootstrap checkout through the fully qualified tag** (`documentation/docs/user-guide/installation.md:127`)
  - Issue: `git clone --branch v0.1.2 --single-branch ...` prefers a branch named `v0.1.2` over the tag of that name. The next commands execute that checkout's `install.sh` and adjacent helper, so the helper's later exact-tag payload fetch cannot enforce which installer code has already run. This contradicts the preceding instruction to use the release's checkout. A local Git fixture with an annotated `v0.1.2` tag and a different same-named branch reproduced a checkout of `heads/v0.1.2`, whose `install.sh` contained the branch content; the cloned HEAD differed from `refs/tags/v0.1.2^{commit}`. No networking or source execution was involved in this reproduction.
  - Fix: Fetch `refs/tags/v0.1.2` explicitly into the bootstrap checkout and detach at the peeled fetched commit before assigning `INSTALLER` or running it. For example, initialize the checkout, fetch the fully qualified tag from the repository with `--no-tags --depth=1`, and check out `FETCH_HEAD^{commit}` with `--detach`. Add a local branch/tag-collision check for this documented bootstrap. The current helper collision test at `tests/tooling/standalone-installer.test.ts:262` already validates the payload reader, but the documentation contract at `tests/release/standalone-install-contract.test.ts:16` only extracts the six final installer commands and does not exercise the bootstrap.
  - Requirement: Discovery decisions 3 and 11, the exact-tag source contract, and p01-t02's pinned first-party procedure. This is a documentation/bootstrap correction; the helper's qualified tag fetch at `scripts/install-standalone.mjs:150` is correct.
