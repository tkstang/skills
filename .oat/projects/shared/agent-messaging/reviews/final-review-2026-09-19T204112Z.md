- **Shipped entrypoints silently no-op when launched through a symlinked path** (`src/skills/session-observer-collab/src/claude-monitor.mjs:531`, `src/skills/agent-messaging/src/hooks/claude-code.ts:88`, `src/skills/agent-messaging/src/hooks/codex.ts:90`)
  - Issue: the Monitor guards `main` by comparing `import.meta.url` with a `file://` URL built from `process.argv[1]`, and both hooks compare `path.resolve(process.argv[1])` with `fileURLToPath(import.meta.url)`. Node resolves `import.meta.url` to the real path while `argv[1]` keeps the invoked path, so any symlink in the path (or a URL-escaped character such as a space for the Monitor) makes the guard false. Reproduced with the generated bundles copied outside the repo: via a real path the Monitor prints `claude-monitor: error` with rc=1 for bad input and the hooks print `SyntaxError`; via a symlinked directory all three exit 0 with no output and never run. The repository's own install convention makes provider entries such as `~/.claude/skills/session-observer-collab` symlinks to `~/.agents/skills/...` (confirmed on this machine), and that symlinked path is the skill base directory a Claude session is given. The composed Monitor therefore never polls, never notifies, and reports nothing, while `delivery register` reports success for a hook that will stay inert. The manual CLI already handles this correctly (`agent-messaging.ts:992-996` uses `realpathSync` on both sides).
  - Fix: use the CLI's `realpathSync(path.resolve(process.argv[1])) === realpathSync(fileURLToPath(import.meta.url))` guard in all three entrypoints (and any other new entrypoint), then add a packaging test that executes each generated entrypoint through a symlinked directory and asserts it actually runs. The same pre-existing pattern in `hooks/codex-stop.mjs:608` and `hooks/cursor-stop.mjs:370` is outside this project's diff but worth aligning in the same change since both files were edited here.
  - Requirement: design §Ownership and packaging ("Copied standalone payload runs with Node alone"); plan p04-t01 Verify (copied bundles execute outside the repo).

None of these four names appears in `SKILL.md`, either runtime reference, the user guide, the architecture page, or any prior review; the reference says only "settings files supplied by the acting environment". With nothing supplied, `inspectClaudeStopInventory` returns zero registrations, zero unreadable sources, and `assessAutomaticOwnership` reports the inventory "accepted". Consequences: (1) on the documented flow, third-party Claude Stop hooks are never disclosed and `--acknowledge-stop-hooks` is never required; (2) even if an operator passes `--settings-paths` at enable and acknowledges a fingerprint, the hook/watch/Monitor recompute an empty inventory from env, so "changed inventory requires renewed acknowledgment; recheck at delivery boundaries" cannot fire; (3) enable-time and boundary-time sources can silently disagree. Design §6 and plan p02-t02 require inspecting loaded user/project/local/managed settings plus enabled installed plugins, and state that unreadable/unresolved required sources "cannot be waived" — an absent source list currently waives everything.

Add fixtures proving the default path discloses a third-party Stop hook and that a post-enable change refuses at the boundary without env setup.

### Medium

- **A pre-slot observation interruption is advertised as a retryable message attempt** (`src/shared/collaboration/claims.ts:625-632`, `src/skills/agent-messaging/src/agent-messaging.ts:895-899`)
  - Issue: `interruptedAttempts` includes every event with no slot. An observation event claim that crashed before its slot (or lost to budget exhaustion) matches, and `status` renders each entry as `interrupted attempt — retry available` with a `delivery retry ... --message <uuid>` command. Reproduced: a `claimObservation` aborted in `afterEventClaim` lists its token in `interruptedAttempts`. This contradicts plan p04-t01 ("Never advertise delivery retry --message or a retry generation for an observation claim") and the runtime reference. The command would fail with `RECORD_CONFLICT`, so the impact is misleading status rather than corruption.
  - Fix: exclude events carrying `observation` from `interruptedAttempts` and `outcomeUnknown` (they are already reported in `observationAttempts` with the manual pinned-read recovery), and assert this in `claims.test.ts` and the CLI status test.

- **The Monitor accepts a `triggered` lease on every composition check, wasting a shared slot and suppressing a new range, and bypassing the final peer-continuity check** (`src/skills/session-observer-collab/src/claude-monitor.mjs:219`)
  - Issue: `if (!inspected.eligible && lease.state !== 'triggered')` was needed so the post-CAS final check passes, but it applies to the initial and per-iteration checks too, and it discards every ineligibility reason once the state is `triggered`, including `verifyAdapterPeerContinuity` failures. Reproduced: after an observation notification (lease `triggered`), starting the Monitor again without re-arm passes composition, reserves a second event and shared slot for the peer's next range, then fails `claimAdapterTrigger` (triggered leases are ineligible), emits nothing, and permanently suppresses that range's event key for the activation. The designed "CAS loss may waste a slot" tradeoff covers races, not this deterministic operator path. Separately, plan p04-t01 requires rechecking peer continuity "immediately before either notification"; after the CAS the state is always `triggered`, so that recheck can never refuse.
  - Fix: require an eligible (`armed`/`waiting`) lease for the initial and per-iteration checks (return a distinct `rearm-required` reason), and for the post-CAS final check accept `triggered` only when `inspected.reason` is the triggered state itself rather than a continuity/identity failure.

- **Monitor outcomes are invisible to the acting agent and its invocation is undocumented** (`src/skills/session-observer-collab/src/claude-monitor.mjs:501-536`, `src/skills/session-observer-collab/references/runtime-claude-code.md:36-62`)
  - Issue: `runClaudeMonitorMain` discards the result, so `stop-confirmation-required`, `activation-mismatch`, `ownership-refused`, `lease-expired`, `duplicate-observation`, `shared-budget-refused`, and `duration-complete` all look identical (exit 0, no output); thrown validation errors print only `claude-monitor: error`. An agent cannot distinguish a quiet 30 minutes from an immediate refusal, contrary to design §6 ("redacted diagnostics to stderr") and plan p04-t01. No document gives the concrete command: `--collab`, `--activation-id`, `--self`, `--peer`, `--cwd`, `--peer-transcript`, and the two `--confirm-*` flags appear nowhere, and the Monitor's `--collab` differs from `arm`'s `--collaboration-id`. The message-notification path also publishes no `output-attempted` diagnostic, unlike the standalone watch (`watch.ts:244-254`) and the Monitor's own observation path.
  - Fix: write one redacted terminal reason line to stderr (never stdout) and use a nonzero exit for refusals; print the `TypeError` message for input validation; publish a `monitor` boundary diagnostic for message notifications; add complete arm/enable/launch/re-arm command examples to the runtime reference and align the collaboration flag name.
