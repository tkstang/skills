### Important

- **Host output can cross activation expiry or a newly conflicting owner after the stated final validation** (`src/skills/agent-messaging/src/hooks/common.ts:173`)
  - Issue: `handleBoundary` samples `finalNow`, validates activation and ownership, then publishes event/slot/message claims without a `beforeFinalValidation` callback. `claimDelivery` subsequently reuses the same fixed `input.now` for its post-claim activation check (`src/shared/collaboration/claims.ts:239`), so time cannot advance during claims and observer lease or hook-inventory changes are not rechecked. An expiry, revocation, armed/triggered observer lease, or changed third-party configuration during claim publication can therefore still be followed by host output, contrary to the required claim-then-final-revalidation order.
  - Fix: pass a fresh-clock, fail-closed `beforeFinalValidation` callback from both host adapters that re-runs activation, exact membership, inventory fingerprint, observer ownership, controller/mechanism, and continuation constraints after all claims and immediately before output. Make `claimDelivery` use a fresh time for its own final status rather than the initial timestamp. Add deterministic tests for expiry and owner/config changes after message claim, not only during reply wait.
  - Requirement: p02-t01 final active-state validation; p02-t02 automatic-delivery ownership recheck.

- **`delivery retry` generations are ignored by prompt/Stop adapters** (`src/skills/agent-messaging/src/hooks/common.ts:194`)
  - Issue: every host boundary claims `retryGeneration: 0`. `createDeliveryRetry` persists a later generation (`src/shared/collaboration/claims.ts:254`), but only the watch path reads retry records (`src/skills/agent-messaging/src/watch.ts:114`). After a Stop attempt claims a message and crashes before emitting, the documented retry command cannot make the next Stop own that message again; generation zero conflicts forever even though the CLI reports a retry record.
  - Fix: centralize delivery-key resolution and have prompt/Stop and watch consume the highest valid retry generation for the current activation/participant. Preserve the native Stop-chain event key so a retry cannot bypass one-continuation-per-chain. Add pre-slot, pre-message, and post-message-claim Stop crash tests that run the CLI retry and prove exactly one later bounded attempt can own the requested message.
  - Requirement: p02-t01 explicit idempotent retry generations and Stop-chain dedup.

- **Human-idle renewal is available without proven host provenance** (`src/skills/agent-messaging/src/agent-messaging.ts:452`)
  - Issue: the public CLI accepts `--expiry-mode human-idle` for any Codex or Claude session and separately exposes `delivery activity --event`, which calls `recordHumanActivity` directly (`src/skills/agent-messaging/src/agent-messaging.ts:549`). The core API checks only that the epoch is human-idle (`src/shared/collaboration/activation.ts:553`); it has no provenance contract. A manual, peer-driven, replayed, or otherwise unverified invocation can therefore extend an activation despite the fixed-expiry fallback required until a host/version has qualifying human-origin evidence.
  - Fix: remove ordinary CLI renewal as an authority-bearing operation and reject human-idle enablement unless the exact adapter/host version has recorded qualifying provenance evidence. Route renewal only through the validated native human event path, with replay-stable event identity, and add negative CLI/core tests showing arbitrary events cannot renew.
  - Requirement: p02-t01 proven human-only renewal; p02-t02 fixed-expiry fallback for unproven provenance.

- **Malformed schema-6 observer leases can be treated as inactive ownership** (`src/skills/agent-messaging/src/registration.ts:265`)
  - Issue: the read-only detector validates only a small locally declared subset of the real schema-6 lease. It ignores required fields and invariants such as lease ID, peer identity/transcript/index contract, wait fields, non-negative bounded counters, updated time, and diagnostic shape, then immediately treats `idle`/`disarmed` as inactive (`src/skills/agent-messaging/src/registration.ts:328`). A partial or semantically invalid record with those few fields can therefore permit standalone delivery instead of producing the required uncertain/manual result. The contract test imports the real `effectiveLease` but does not prove the detector applies equivalent validation.
  - Fix: implement a pinned, complete, non-mutating schema-6 validator equivalent to the exported observer contract before applying effective state, and treat every missing/invalid field as uncertainty. Extend the drift tests with partial idle/disarmed records, invalid counters/wait fields, invalid path identity, and future schema versions.
  - Requirement: p02-t02 invalid/unknown observer state fails closed and only validated idle/disarmed is inactive.

- **Third-party acknowledgment fingerprints omit effective hook configuration** (`src/skills/agent-messaging/src/registration.ts:42`)
  - Issue: the fingerprint hashes only `{source, command}` and `stopCommands` discards matcher/scope, type, timeout, and other registration fields (`src/skills/agent-messaging/src/registration.ts:58`). A third-party Stop registration can materially change when/how it runs while retaining the same command, yet delivery continues under the old immutable acknowledgment. Existing tests change only the command.
  - Fix: fingerprint the canonical effective Stop registration objects, including matcher/scope and execution options that affect continuation interference, while excluding only demonstrably irrelevant serialization noise. Disclose that same normalized structure and test same-command changes to matcher, timeout, type, group structure, and plugin source resolution.
  - Requirement: p02-t02 exact scoped inventory acknowledgment and renewed acknowledgment on configuration change.

- **Diagnostic identifiers can escape their namespace and diagnostic “codes” accept raw text** (`src/shared/collaboration/diagnostics.ts:28`)
  - Issue: `attemptId` is only a bounded string and is interpolated directly into `diagnostics/<attemptId>.json` (`src/shared/collaboration/diagnostics.ts:80`), so path separators and `..` can target another location under the collaboration root. `outcomeCode` and `errorCode` likewise accept arbitrary 64-byte strings; the small keyword regex does not implement the required code allowlist and can persist paths, headers, or raw host errors that avoid those words.
  - Fix: use strict path-safe identifier and code grammars (or hash identifiers before path use), assert the resolved diagnostic target remains directly under the exact diagnostics directory, and validate the full record again on read. Replace free-form outcome/error strings with closed enums or an explicitly versioned allowlist, then add traversal, non-keyword secret/raw-error, malformed-read, and capacity tests.
  - Requirement: p02-t01 allowlisted bounded identifiers/codes, redaction, and immutable diagnostic confinement.

- **Probe timeouts do not stop the timed operation and can report cleanup while work is still running** (`src/skills/agent-messaging/src/probe.ts:216`)
  - Issue: `withTimeout` is a bare `Promise.race`; it does not cancel `setup` or `invoke`. After timeout, an adapter can continue launching or mutating resources while `finally` runs cleanup with an empty or incomplete ownership list, and the function may return `cleanupVerified: true` even though the timed operation remains live (`src/skills/agent-messaging/src/probe.ts:264`). The timeout test uses a never-settling promise and checks only the returned label, so it misses late side effects/resource leaks.
  - Fix: make setup/invoke abort-aware, transfer owned-resource identity incrementally before blocking work, await confirmed termination, and report cleanup verified only after the timed operation is quiescent and every owned resource is checked. Add late-resolution/late-side-effect tests for setup and invoke plus interruption during an in-flight event.
  - Requirement: p02-t04 bounded time/resource use, interruption handling, and verified cleanup of owned registrations/processes.

### Medium

- **On-read activation validation does not enforce the 24-hour hard-cap relationships** (`src/shared/collaboration/activation.ts:145`)
  - Issue: stored records are checked for parseable timestamps and content hash, but not that `hardExpiresAt` is after `startedAt` and at most 24 hours later, nor that fixed expiry is within that hard deadline. `effectiveActivationExpiry` then trusts those values (`src/shared/collaboration/activation.ts:310`). A semantically malformed but canonically hashed record can therefore extend automatic delivery beyond the approved cap instead of failing closed.
  - Fix: validate all timestamp relationships and nested acknowledgment/attestation invariants on every load, then add correctly hashed malformed-record fixtures for overlong, reversed, and mismatched epochs.
