### Medium

- **The activation remains active at its exact expiry timestamp** (`src/shared/collaboration/activation.ts:455`)
  - Issue: `activationStatus` expires an activation only when `now` is strictly greater than `effectiveExpiresAt`. At equality it returns `active: true`, so a prompt or Stop boundary sampled at the fixed, idle, or hard deadline may still claim and emit. The approved contract describes a finite expiry and an absolute lifetime cap, so the deadline itself should be inactive.
  - Fix: change the comparison to `>=` and add fixed-expiry, human-idle, and hard-cap tests at exact equality, including one adapter-level no-output case.
  - Requirement: p02-t01 finite expiry and 24-hour absolute cap; design section 5 finite activation.

- **A diagnostic can record host output before the final output veto succeeds** (`src/skills/agent-messaging/src/hooks/common.ts:271`)
  - Issue: the adapter publishes stage `output-attempted` / outcome `host-output-attempted` and only then performs the last ownership/expiry validation at line 285. If that last check fails because the activation, inventory, or observer owner changed during diagnostic publication, the function returns no host output while status retains a false output-attempt record.
  - Fix: do not publish `host-output-attempted` until the adapter has actually crossed the final veto and attempted stdout. If the common handler must remain side-effect-free with respect to stdout, return attempt metadata to the host-specific main and publish the outcome after `process.stdout.write`; otherwise use a pre-output diagnostic code that does not assert an attempt.
  - Requirement: p02-t01 diagnostics must report the actual latest event/outcome and must not fabricate delivery-stage evidence.
