- **Schema-v1 readers accept structurally invalid and hash-forged authoritative records** (`src/shared/collaboration/records.ts:70`)
  - Issue: `assertSchema` checks only that the value is an object with `schemaVersion: 1`; `readJsonRecord<T>` then casts it to any requested record type. It does not validate required fields, UUIDs, generations, enum values, timestamps, path/record identity, or content hashes. A targeted copied-runtime probe inserted a message with `kind: "unsupported-kind"` and `contentHash: "not-a-real-hash"`; `inbox` returned it as a legitimate message.
  - Impact: Corruption or malformed authoritative state can be surfaced as valid mail, suppress messages through malformed receipts, select invalid bindings, or crash later sorting/identity logic instead of failing the affected operation closed.
  - Fix: Add record-specific validators and invoke them on every read. Validate all modeled fields and path keys, recompute message/log hashes, and add malformed-but-schema-1 fixtures for every authoritative record type.
  - Requirement: p01-t01 schema-v1 validation and the approved malformed/unknown-record fail-closed contract.

- **A crash between alias and generation-zero binding publication permanently strands the alias** (`src/shared/collaboration/membership.ts:141`)
  - Issue: Join first publishes `members/<alias>.json`, then separately publishes `bindings/<participant>/0.json`. If the process ends between those writes, retry generates a new participant ID, loses the alias publication race, and calls `resolveMember`, which fails because no binding exists. A targeted fixture reproducing that post-alias state returned `MEMBER_NOT_FOUND` on every join retry.
  - Impact: One interrupted join can make a required alias unusable indefinitely; v1 intentionally has no broad cleanup/repair command, so the approved identical-retry and crash-recovery semantics are not met.
  - Fix: Publish the generation-zero binding inside the exclusive alias record as designed, or introduce a deterministic, validated recovery protocol that can complete an exact orphaned join without redirecting or overwriting a competing winner. Add process-kill coverage at this boundary.
  - Requirement: p01-t02 idempotent exact join and the approved alias-record design.

- **Writers and acknowledged-history output do not enforce the declared bounds** (`src/shared/collaboration/messages.ts:195`)
  - Issue: Join, send, and log append publish without a pre-publication soft-cap check; only readers later enumerate with caps. Sequential writes can therefore report success beyond 128 members, 4,096 messages, or 4,096 log entries and then make ordinary resolution/inbox/log reads fail with `CAPACITY_EXCEEDED`. Separately, `listInbox` applies the 8-message/48-KiB result limit only to pending mail and returns every acknowledged full record when `includeAcknowledged` is true (`src/shared/collaboration/messages.ts:302`), which affects both `inbox --all` and `status`.
  - Impact: A sender can successfully enqueue state that bricks later readers, while acknowledged history can expand a nominally bounded CLI result to roughly the full 4,096-message directory and its bodies.
  - Fix: Apply bounded preflight counts before sequential publication while retaining the documented soft concurrent-overrun semantics, and bound/paginate the combined pending/acknowledged result or return counts/IDs for history and status. Test the boundary and one-over cases.
  - Requirement: p01-t01 bounded enumeration/capacity and p01-t03 bounded manual reads.

- **The manual CLI silently ignores `--reply-to`** (`src/skills/agent-messaging/src/agent-messaging.ts:296`)
  - Issue: `sendMessage` supports reply references, but the CLI never parses or passes `--reply-to`. The generic parser accepts the flag without complaint, and a targeted copied-runtime probe showed the stored message's `replyTo` remains `null`.
  - Impact: Users cannot create the approved durable reply relationship through either shipped distribution, and the silent acceptance makes the command appear successful while discarding requested semantics.
  - Fix: Parse `<participantId>/<messageId>`, validate both UUIDs, pass the reference to `sendMessage`, document it in the skill/user guide, and add positive, malformed, unrelated-participant, and copied-payload tests.
  - Requirement: p01-t03 reply references and p01-t05 CLI parity with the approved design.

- **Closed and inactive outcomes map to the wrong CLI exit class** (`src/skills/agent-messaging/src/agent-messaging.ts:190`)
  - Issue: `exitFor` maps every `MembershipError` to exit 2 before considering closed/inactive outcomes. A targeted copied-runtime probe confirmed a join against a closed collaboration returns code `COLLABORATION_CLOSED` with process exit 2; departed/inert membership paths are likewise mapped to exit 1 or 2 rather than 3.
  - Impact: Scripts cannot reliably distinguish invalid identity/input from the stable closed/inactive capability state promised by the public skill documentation and design.
  - Fix: Map `COLLABORATION_CLOSED`, `MEMBER_DEPARTED`, and other explicitly inactive/unavailable outcome codes to exit 3 while retaining stale/invalid identity at exit 2; add command-level tests for join, takeover, inbox, send, leave, and close states.
  - Requirement: p01-t05 JSON/exit contract.

- **Post-publication message checks miss closure and recipient-takeover races** (`src/shared/collaboration/messages.ts:208`)
  - Issue: After publishing, `sendMessage` rechecks only the sender generation. It does not recheck `closed.json` or the addressed recipient generation, and inbox readers do not compare `message.to.generation` with the current binding before presenting the record.
  - Impact: A send that loses a close or recipient-takeover race returns ordinary `queued: true` with no closed/in-flight or stale-address warning, contrary to the approved requirement that final readers validate generations and report the race rather than treating stale ownership as current.
  - Fix: Revalidate closure plus both sender and recipient bindings after publication, carry an explicit race status in the result, and have inbox/status label inert closed or stale-generation records without deleting or silently retrying them. Add deterministic close/send and takeover/send orchestration tests.
  - Requirement: p01-t03 close/stale-binding race reporting and design closeout semantics.

- **`log show` follows a symlinked rendered view and returns arbitrary file contents** (`src/shared/collaboration/log.ts:274`)
  - Issue: Authoritative JSON reads reject symlinks and wrong file types, but `getLogView` calls `readFile` directly on `collaboration.md`. A targeted copied-runtime probe replaced that view with a symlink to another file and `log show` returned the target contents.
  - Impact: The shipped inspection command violates the explicit symlink/type/owner/containment contract and can disclose an unintended file through its JSON output.
  - Fix: Inspect the rendered view with `lstat`, reject symlinks and non-regular/wrong-owner files, enforce canonical containment and a bounded size before reading, and add symlink/owner/oversize fixtures for show and render.
  - Requirement: p01-t01 safety and p01-t04 rendered-view inspection.
