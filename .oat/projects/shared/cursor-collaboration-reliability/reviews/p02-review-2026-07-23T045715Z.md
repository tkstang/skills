### Important

- **Compatibility rollback can delete an unbacked legacy Cursor entry and strand migration** (`src/transcript/session-observer/lib/state.ts:645`)
  - Issue: `markRead('cursor', ...)` reads `cursor-state.json`, then writes a compatibility entry under the independent legacy lock, then rechecks Cursor state. If migration writes a nonzero `legacyUnverified` marker after the first read but before the legacy write, the second check rejects and the rollback at line 690 deletes the compatibility entry instead of restoring the exact legacy preimage. Migration has not necessarily written its backup yet, so retry observes both a missing legacy entry and missing backup and fails with `LEGACY_BACKUP_MISSING`. This was reproduced by pausing the legacy write after the initial Cursor-state check, inserting the valid marker, and resuming: the legacy sessions map became empty and migration could no longer complete. The behavior violates the p02-t03 recoverable-migration ordering contract and FR4/FR6/NFR3.
  - Fix: Serialize migration and transitional `markRead` through one consistent dual-store transaction/order, or add a durable compatibility-transition marker that makes every interleaving replayable. Never blindly delete on rollback; restore the exact captured legacy preimage. Add deterministic tests for marker creation between the precheck and legacy write, process failure after each store write, and retry from every resulting state.
  - Requirement: FR4, FR6, NFR3

- **Corrupt or invalid v2 state is silently converted into fresh empty state** (`src/transcript/session-observer/lib/cursor-state.ts:541`)
  - Issue: `readCursorState()` backs up malformed JSON or an invalid schema, then returns `emptyCursorState()` at lines 552-563. The next ordinary mutation writes that empty value over `cursor-state.json`, erasing the only active observation cursor, continuity checkpoint, open-turn reconciliation, and delivery reservation without an explicit reset. This was reproduced by loading a corrupt file and calling `mutateCursorState(state => state)`; the corrupt state became a valid empty schema. Later stateful observation cannot distinguish this from a never-observed session and may replay content without the required fail-visible recovery path. The design requires schema/identity-state mismatch to leave state unchanged and exit through a structured mismatch.
  - Fix: After making the backup, return a stable corruption/schema error or durable recovery-required marker; do not expose an empty state to mutators. Require explicit reset/replay before a new v2 entry can be created, and add tests proving load and every mutation path fail closed without replacing the corrupt file.
  - Requirement: FR4, FR6, NFR3

### Medium

- **A valid repair is rejected when it shortens only the unverified blocking tail** (`src/transcript/session-observer/lib/cursor-state.ts:89`)
  - Issue: continuity blocks whenever current file size is below `checkpoint.observedSize`, but `observedSize` includes bytes after `safePrefixBytes`. A long partial or malformed blocking frame can be replaced by a shorter valid closed frame while preserving the exact verified prefix, path, device, and inode. The implementation returns `TRANSCRIPT_SHRANK` before checking that preserved prefix. The existing repair test covers only a replacement that grows the file; an adversarial shorter repair reproduced the false block. FR4 explicitly requires a repaired blocking frame to resume from the last verified checkpoint.
  - Fix: Base unsafe shrink detection on the verified checkpoint boundary, not unverified tail length. Permit replacement of bytes at or after `prefixBytes` when path/device/inode and `verifiedPrefixSha256` still match, while continuing to block shrink or mutation inside the verified prefix. Add shorter partial-tail and malformed-frame repair tests.
  - Requirement: FR4, NFR5

- **Delivery CAS accepts and commits a backward checkpoint** (`src/transcript/session-observer/lib/cursor-state.ts:312`)
  - Issue: pending-delivery validation requires only `intendedCheckpoint.nextFrameIndex === reservedThroughFrameIndex + 1`; it never relates that range to `expectedNextFrameIndex` or checks monotonic prefix advancement. A reservation with expected frame 3, reserved-through frame 1, and intended frame 2 is accepted, and `commitCursorDelivery()` then rewinds the durable cursor from 3 to 2. This was reproduced against the generated runtime. The API therefore does not enforce the monotonic accounting invariant it is intended to protect.
  - Fix: Reject reservations whose delivery range starts behind the expected checkpoint or whose intended checkpoint regresses frame/prefix identity. Validate same file identity/index base and a verified, nondecreasing prefix boundary before reservation, and repeat the invariant at commit. Add backward-frame, backward-prefix, and mismatched-file CAS tests.
  - Requirement: FR6, NFR5
