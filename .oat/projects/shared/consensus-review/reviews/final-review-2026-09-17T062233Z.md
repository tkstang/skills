### Important

- **Shared `detectHostRuntime` now returns `unknown` in multi-marker environments, weakening the recursion guard for existing Consensus workflows** (`src/plugins/consensus/provider-cli/host-guard.ts:38`)
  - Issue: Before this project, `detectHostRuntime` used a priority order (Claude → Codex → Cursor), so an environment with markers from two providers still resolved to a known host. It now returns `unknown` whenever `detectedHostRuntimes` yields more than one entry (`host-guard.ts:41-42`, `host-guard.ts:201-231`). `hostContextFromEnv` (`host-guard.ts:98-110`) feeds that value to every existing caller (`args.ts:703`, `args.ts:717`, `commands.ts:386`), and `evaluateHostGuard` treats `unknown` as `allowed('unknown', 'none')` with no `child_env` (`host-guard.ts:127-129`). Consequently, for Create/Decide/Plan/Refine/Evaluate/Panel runs launched from a shell that carries two providers' markers (for example Claude Code inside Cursor's integrated terminal, or this gate run, which has both `CURSOR_AGENT` and `CODEX_SESSION_ID` set), the child peer no longer receives `CONSENSUS_PARENT_HOST`/`CONSENSUS_DEPTH`, so the max-depth recursion guard is silently disabled where it previously engaged. Reproduced against canonical source: `detectHostRuntime({ CLAUDECODE: '1', CURSOR_TRACE_ID: 'trace' })` → `unknown`; `evaluateHostGuard({ host: hostContextFromEnv(thatEnv, '/repo', 1), provider: 'claude' })` → `{ allowed: true, guard: 'none' }` with no `child_env`. The base revision returned `claude` and propagated depth. Plan p06-t02 explicitly required "Keep existing caller defaults"; this change is not recorded in `CHANGELOG.md`, `implementation.md`, or the docs, and `host-guard.test.ts:17-22` only covers single-marker inputs, so the regression is untested.
  - Fix: Restore deterministic resolution for the shared detector: give an explicit known `CONSENSUS_PARENT_HOST` value precedence, then fall back to the prior priority order when multiple ambient markers are present, so `detectHostRuntime` never regresses from a known host to `unknown` for existing callers. Keep the strict "exactly one detected runtime must equal the declared runtime" rule confined to Review's `resolveExplicitHostContext` if desired (see M1 for a compatible relaxation). Add `host-guard.test.ts` cases for `{CLAUDECODE, CURSOR_TRACE_ID}` and `{CONSENSUS_PARENT_HOST: 'codex', CURSOR_AGENT}` asserting the resolved host and that `evaluateHostGuard` still emits `child_env` with incremented depth. Any intentional semantic change to the shared detector must bump the affected consumer skill versions and add a `### Changed` entry under `## [Unreleased]`.

### Medium

- **Review's explicit-host resolution treats an explicit `CONSENSUS_PARENT_HOST` declaration plus one ambient marker from another provider as contradictory, blocking Review in nested and mixed environments** (`src/plugins/consensus/provider-cli/host-guard.ts:46-66`)
  - Issue: `resolveExplicitHostContext` fails with `contradictory_host` whenever `detected.size > 1`, without giving an explicit known `CONSENSUS_PARENT_HOST` any precedence. Reproduced: `resolveExplicitHostContext({ runtime: 'claude', env: { CONSENSUS_PARENT_HOST: 'claude', CURSOR_TRACE_ID: 'trace' }, maxDepth: 1 })` → `contradictory_host`; with this gate's live environment, `--host cursor`, `--host codex`, and `--host claude` all fail the same way. Because `runReview` calls this before any dispatch (`src/skills/consensus-review/src/run.ts:124-132`), Review returns `predispatch_failed` with zero invocations in exactly the nested/agent-launched setups the skill is meant to serve, and only after scope capture, run-state creation, evidence persistence, and reviewer preflight probes have already run. The design says "unknown or contradictory identity blocks", but an ambient marker from a different tool is not a contradiction of an explicit, matching parent declaration. Neither `documentation/docs/user-guide/consensus/review.md` nor `SKILL.md` explains that `--host` is verified against runtime markers, that a marker-free shell fails with `unknown_host`, or that `CONSENSUS_PARENT_HOST` can supply the evidence, so operators receive an opaque failure.
  - Fix: In `resolveExplicitHostContext`, when `CONSENSUS_PARENT_HOST` is a known value, treat it as the authoritative declaration: fail `contradictory_host` only if it differs from `runtime`; ignore ambient markers in that case. When it is absent, keep requiring that the detected set is exactly `{runtime}`. Extend `host-guard.test.ts` and `run.test.ts` with the explicit-parent-plus-ambient case (allowed) and the explicit-parent-mismatch case (blocked). Document in `review.md` (a short "Host identity" note under "Run a review") that `--host` must match detected runtime evidence, that a plain shell needs `CONSENSUS_PARENT_HOST=<runtime>`, and what `unknown_host` / `contradictory_host` mean. Bump `consensus-review` `metadata.version` and add a changelog line.

### Minor

- **Receipt fixtures are pinned by hash but not tied to `renderReviewMarkdown`, so renderer drift would not invalidate the receipt evidence** (`tests/tooling/consensus-review-receipt.test.ts:63-70`)
  - Issue: `clean-review.md` and `findings-review.md` follow the renderer's exact section layout (`# Consensus Review`, `## Scope and provenance`, `### Authorship evidence`, `## Checks reported`, …) and are the fixtures the independent receipt exercise consumed (`evidence/p08-receipt-exercise.md`). The suite only asserts their SHA-256 and a few substrings; `review.test.ts` never renders an aggregate and compares it to these files. A future change to `renderReviewMarkdown` (`src/skills/consensus-review/src/review.ts:236-330`) would leave the fixtures untouched and the "receivable" claim stale without any failing test.
  - Suggestion: Add a `review.test.ts` case that builds the two deterministic aggregates and asserts `renderReviewMarkdown(aggregate)` equals the fixture bytes (or regenerate the fixtures from the renderer in that test with a `UPDATE_FIXTURES` guard), so the pinned hashes and the renderer move together and the receipt evidence stays attributable to real output.

- **`--request-file` follows symlinks and opens without a pre-open regular-file check, so a FIFO or device path can block or be read before rejection** (`src/skills/consensus-review/src/review.ts:506-532`)
  - Issue: `readBoundedText` calls `openFile(targetPath, O_RDONLY)` and only then checks `isFile()`. A FIFO blocks at `open` until a writer appears; a symlink to a special file is followed. Document and scope inputs use `lstat`/`realpath` before reading (`scope.ts:495-547`), so the request file is the one bounded input without that pre-check. Impact is limited to a caller-supplied path, so this is a robustness gap rather than a security boundary.
  - Suggestion: `lstat` the resolved path first and reject non-regular files and symlinks with a `request_file_invalid` usage error, or open with `O_RDONLY | O_NOFOLLOW | O_NONBLOCK` before `stat`, mirroring the document path handling.
