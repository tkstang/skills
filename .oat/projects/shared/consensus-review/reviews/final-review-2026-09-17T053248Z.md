### Important

- **I1 — Output failure can leave a partial receivable artifact and advertise a diagnostic that was never written** (`src/skills/consensus-review/src/review.ts:589`)
  - Issue: `writeExclusive` opens the final `review.md` or exported destination directly with `wx`, then writes and syncs in place. If `writeFile` or `sync` fails after the path is created, the final path remains as an empty or partial completed-review artifact. The error path then calls `localOutputFailure`, whose diagnostic write failure is swallowed at lines 621-625 even though its returned JSON and human output always name that diagnostic path. This violates the complete-artifact-only rule and the handoff contract that paths name artifacts actually written.
  - Fix: Publish Markdown through a same-directory private temporary file that is fully written and synced before a no-clobber atomic publication step; remove the temporary file on every failure and ensure no partial final path survives. Make diagnostic persistence report success explicitly, and include a diagnostic path only when that file was actually created. Add fault-injection tests for canonical write, export write, sync, and diagnostic-write failures.
  - Requirement: `design.md` lines 121 and 138; only complete, valid, stable results are receivable and handoff paths must identify artifacts actually written.

### Medium

- **M1 — A growing request file can bypass the declared 256 KiB bounded read** (`src/skills/consensus-review/src/review.ts:488`)
  - Issue: `readBoundedText` checks the open file's size once, then calls `handle.readFile` without a read limit or post-read byte check. Another process can append after `stat` and before or during the read, causing the CLI to allocate and ingest more than `REQUEST_FILE_MAX_BYTES`. Later prompt construction rejects an oversized string before provider invocation, but the bounded input/read guarantee has already been bypassed.
  - Evidence: A no-provider probe opened a 204,800-byte request, appended it to 409,600 bytes after the size check, and the same handle returned all 409,600 bytes despite the 262,144-byte limit.
  - Fix: Read from the already-open handle in bounded chunks up to `REQUEST_FILE_MAX_BYTES + 1`, rejecting on the first excess byte, or reuse a helper with equivalent bounded-allocation semantics. Add a deterministic growth-seam regression proving an appended request is rejected with zero provider invocations and without reading an unbounded buffer.
  - Requirement: p07 bounded request input and the design's bounded capture/failure-before-dispatch contract.
