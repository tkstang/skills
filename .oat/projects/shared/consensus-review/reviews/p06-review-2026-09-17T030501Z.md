### Important

- **I1 — The external Codex capture check can write through a symlink into the reviewed worktree** (`src/skills/consensus-review/src/run.ts:221`)
  - Issue: `reviewTransport` requires an absolute path, then compares only `path.resolve(input.codexCapturePath)` with `path.resolve(input.cwd)` using the lexical `inside` predicate. It does not resolve the worktree or the capture target's nearest existing ancestor canonically, reject symlink aliases, or require a non-destructive caller-owned destination. An outside path whose parent is a symlink to a directory inside the worktree passes and is forwarded as `--output-last-message`; the provider CLI can therefore truncate or create a file inside the supposedly read-only reviewed worktree. The same seam also accepts arbitrary pre-existing external destinations, including aliases of other inputs.
  - Evidence: A no-provider fixture created an outside symlink to `<worktree>/.review` and passed `<outside-symlink>/last-message.json`. `runReview` reached the injected turn with `invocation_count: 1` and forwarded that path, whose canonical destination was `<worktree>/.review/last-message.json`. The existing test covers only a lexically in-worktree path.
  - Fix: Canonicalize the reviewed worktree and the capture path through its nearest existing ancestor before dispatch; reject canonical containment, symlink/input aliases, and unsafe pre-existing destinations. Prefer requiring a verified private external run root and an absent/exclusively created capture target. Add installed/source tests for symlinked parent directories, a symlinked capture file, worktree aliases, pre-existing targets, and the normal external path.
  - Requirement: design.md lines 20, 55, 67, 74, 79, 85 and plan.md p06-t02 external Codex capture/read-only transport.

- **I2 — Malformed inherited depth resets the recursion budget to zero** (`src/plugins/consensus/provider-cli/host-guard.ts:81`)
  - Issue: `resolveExplicitHostContext` evaluates `parseNonNegativeInteger(CONSENSUS_DEPTH) ?? 0`. When the inherited variable is present but malformed, the resolver silently treats the process as a root invocation. A nested peer can therefore replace the inherited depth with a malformed value and obtain another allowed depth-one dispatch, contrary to the fixed maximum-depth-one contract.
  - Evidence: A no-provider fixture invoked the installed runner with `CONSENSUS_PARENT_HOST=codex` and `CONSENSUS_DEPTH=malformed`. Preflight received `{ depth: 0, max_depth: 1 }` and the injected turn ran once instead of returning a zero-invocation preflight failure. Current tests cover a valid inherited depth and unknown/contradictory runtime markers, but not a present invalid depth.
  - Fix: Distinguish an absent depth (root default zero) from a present invalid, non-safe, or out-of-range value. Fail closed with an explicit host-context error before preflight/dispatch, and add source plus installed-bundle coverage showing malformed inherited depth returns `invocation_count: 0`.
  - Requirement: discovery.md decision 2, design.md lines 20 and 67, and plan.md p06-t02 identical explicit host/depth handling with maximum depth one.
