### Medium

- **Correlation's matched/unmatched accounting is computed but never reaches either consumer** (`src/shared/transcript/activity/correlate.ts:213`)
  - Issue: `correlateActivity()` builds `correlationCounts` (owned/inherited/unknown response-stream calls, matched/unmatched results, linked/standalone item evidence), but `ActivityReport` (`src/shared/transcript/activity/types.ts:295-314`) has no field for it and `buildReport()` (`src/shared/transcript/activity/project.ts:485-509`) never reads it. A repository-wide search finds only three non-test references, all hand-written zero literals in the unavailable-activity fallbacks (`digest.ts:1102`, `digest.ts:1467`, `session-export-transcript.ts:758`). `design.md:143` specifies that Coverage carries "Counts for captured, delivered, displayed, omitted, unmatched calls/results", and there is no unmatched-*call* count anywhere. In the shipped report a consumer can detect an unmatched result only per event (absent `relatedCallKey`), cannot see unmatched totals for omitted groups, and cannot distinguish an unfinished call from a completed one without a client-side join (see the related Low on call outcome). The mechanism's only live consumer today is its own tests.
  - Fix: choose one direction and make code, design, and docs agree. Either (a) surface the counts — add a scoped `correlation` block to `ActivityReport` (captured and delivered scope), include unmatched calls, render one line in `renderActivityMarkdown`, and extend `project.test.ts` to pin it under the byte guard; or (b) treat this as artifact alignment — amend `design.md` Data Models to state that unmatched evidence is expressed per event, and remove the unused `correlationCounts` plumbing and the three zero literals so the type does not advertise accounting that is never delivered.
  - Requirement: discovery Success Criteria 2 and 6; design Data Models → Coverage.

### Low

- **One-shot `--json` output pretty-prints the digest, so the emitted activity object exceeds the documented rendered limit** (`src/skills/session-observer/src/session-observer.ts:683`)
  - Issue: the byte guard measures the compact `stableActivityStringify` form, but `review --json` and `catch-up --json` emit `JSON.stringify(digest, null, 2)` (also `session-observer.ts:368`). Measured on a 3,000-invocation Claude probe: review reports `renderedBytes` 130,641 against the 131,072 limit while the emitted activity object is 146,251 bytes; catch-up reports 30,720 against 32,768 and emits 34,658. Watch JSON lines are compact and honest. `src/skills/session-observer/SKILL.md:112-115` presents these as the rendered activity limits without that qualifier.
  - Suggestion: either emit compact JSON when `--include-activity` is set, or document that `renderedBytes` and the limits describe the compact serialization and that pretty-printed one-shot output is roughly 10–12% larger.

- **Claude/Codex `call` events stay `pending` even when a correlated result establishes the outcome** (`src/shared/transcript/activity/claude-code.ts:236`)
  - Issue: call events are extracted with `outcome: 'pending'` (`codex.ts:265`, `codex.ts:314` likewise) and correlation never reconciles them, so an export shows `call "Bash"; pending` immediately followed by `result "tool_result"; success`. Keeping evidence on the event that recorded it is defensible, but no skill or user-guide page explains that a call's own outcome is always `pending` and that the related result or item carries the outcome. A consumer filtering `kind=call, outcome=pending` sees every call ever made.
  - Suggestion: document the convention next to the outcome vocabulary in `SKILL.md` and the user guides, or project a derived, clearly labelled `resolvedOutcome` from the exact-ID-related result without altering the native evidence.

- **The Cursor activity range end and the persisted settled checkpoint are derived from different bounds** (`src/skills/session-observer/src/lib/observe.ts:1334`)
  - Issue: `activityEndFrame` calls `settledNextFrameIndex(selected, safeThroughFrame + 1, …)`, while the checkpoint that is actually persisted calls the same helper with `digest.range.nextIndex` (`observe.ts:1422-1426`), which `digest.ts:843-845` can lower to `stabilityWaitFrom`. Exactly-once delivery depends on these two values agreeing. I could not produce a divergence — a throwaway probe covering a settled turn followed by an open turn, and an earlier unterminated turn followed by a settled one, delivered each call exactly once and advanced the checkpoint consistently — so this is a regression-proneness note, not a demonstrated defect.
  - Suggestion: derive both from one value (compute the intended settled checkpoint once and reuse it as the activity range end), or add an assertion/test that pins their equality under a stability wait.

- **The recorded rationale for deferred m4 does not match projection behavior** (`.oat/projects/shared/session-fidelity/implementation.md:660`)
  - Issue: the m4 disposition says metadata "is dropped first under byte pressure". `compareLowPriority` (`src/shared/transcript/activity/project.ts:170-176`) orders removal by failure then recency only, with no kind term. In the 3,000-invocation probe the byte guard retained 6–10 `assistant-metadata` events while omitting about 2,960 call groups, so recent metadata does displace older invocations. The impact is a few hundred bytes per retained metadata event, so deferral remains acceptable; the stated reason is what is wrong.
  - Suggestion: correct the ledger wording, and when m4 is picked up, add a kind term so metadata-only groups are removed before invocation groups.

- **A gate liveness log with machine-local absolute paths is tracked in the project** (`.oat/projects/shared/session-fidelity/reviews/exit-gate-b6a66107-9461-4400-8fdc-fdcf8da6bc5f-stderr.log`)
  - Issue: the tracked 60-line stderr log and its companion `-result.json` record `/Users/<user>/.claude/projects/...` probe paths and temp-dir run markers. No credential or token pattern was found, but this is machine-local provenance rather than a durable review record, and it will travel with the published stack.
  - Suggestion: keep the durable gate outcome already summarized in `implementation.md`, and move raw gate stdout/stderr envelopes to an ignored project-local path (or drop them before the final PR).
