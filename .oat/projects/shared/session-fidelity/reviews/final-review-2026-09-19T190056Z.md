### Minor

- **Item-to-call linking uses `payload.id`, which the maintained schema page says never to correlate on** (`src/shared/transcript/activity/correlate.ts:160`)
  - Issue: `relatedCall()` links an `item_completed` item to a response-stream call when `item.id` equals the call's `nativeId`, and `nativeId` is populated from `function_call.payload.id` (`src/shared/transcript/activity/codex.ts:253`). `documentation/docs/engineering/architecture/session-schemas/codex.md:202` states that field is "**Not** the call id… Never correlate on it", and lines 280-289 say the only observed `item.id` alignment is with `call_id` and should not be built on. The equality check is an exact native-string match, so a false link is unlikely, but the code path and the documented contract disagree, and the one alignment the corpus did observe (`item.id == call_id`) is not the one implemented.
  - Suggestion: either restrict item linking to the explicit `call_id` relation, or document in the schema page and `transcript-core.md` why `payload.id` equality is accepted as corroborated evidence. Add a regression that pins the chosen behavior.

- **Response-stream `web_search_call` keeps no input when the query is nested** (`src/shared/transcript/activity/codex.ts:317`)
  - Issue: the web-search call reads only a top-level `payload.query`. The only tested carrier is the 0.142.x `event_msg` shape. A `response_item` of type `web_search_call` that nests its query (for example under `action`) still produces a counted `call` event, but with no `arguments`, so the projected invocation has no input preview and no `unsupported` coverage signal. This shape was not observed in the evidence corpus, so this is a robustness gap rather than a demonstrated defect.
  - Suggestion: when `query` is absent, retain the native `action` (or the whole payload minus reasoning) as `originalArguments`, or emit `record-activity: unsupported` so the gap is visible instead of silent.

- **Cursor `--include-activity` export normalizes conversation from the frame scanner instead of `readRecords()`** (`src/skills/session-export-transcript/src/session-export-transcript.ts:826`)
  - Issue: with the flag on, Cursor conversation entries come from `cursorCapture.records`. The frame scanner classifies any unterminated final line as `partial` with `record: null` (`src/shared/transcript/cursor-frames.ts:205-224`), while `readRecords()` decodes a valid final record that lacks a trailing newline. In that edge case the conversation section of an activity export drops a message that the default export includes, which departs from design's "each explicitly selected activity export contains the normal sanitized conversation".
  - Suggestion: keep `readRecords()` as the conversation source in both modes and use the frame scan only for activity, or add a test that pins the intended behavior for a valid no-newline tail.

- **Every Claude assistant record yields an uncapped `metadata` event, so activity watch deltas fire without tool activity** (`src/shared/transcript/activity/claude-code.ts:207`)
  - Issue: `assistant-metadata` (model/timestamp) is emitted per assistant record. These groups are exempt from the invocation cap (`project.ts:521-527` caps only groups with an in-range call) and count as events in `prepareActivityDelta()` (`src/skills/session-observer/src/lib/watch.ts:306`), so a thinking-only or otherwise conversation-empty assistant record produces an `activityOnly` delta that carries nothing but a model name and timestamp, even under `--quiet-empty`. Under byte pressure they are correctly dropped first (verified: a 20,000-invocation probe displayed only call/result groups), so this is noise, not data loss.
  - Suggestion: collapse repeated identical model metadata, or exclude metadata-only groups from the `hasEvents` renderability signal while keeping them in delivered reports.

- **Saved-position validation re-reads the transcript and repeats legacy malformed-line warnings** (`src/skills/session-observer/src/lib/state.ts:674`)
  - Issue: `validateSavedPosition()` calls `readRecords()` and `buildDigest()` reads the same file again, so every stateful catch-up and watch poll with a nonzero offset parses the transcript at least twice, and each malformed interior line is reported through `console.warn` once per read in flag-off mode. This is the "repeated transcript reads / duplicate warnings" item already dispositioned `deferred_follow_up` at p01; it remains accurate at the final head.
  - Suggestion: thread one captured read through validation and digest construction (the `capturedRead` option already exists on `buildDigest`).

- **Deferred p01 Minor follow-ups are not captured outside `implementation.md`** (`.oat/projects/shared/session-fidelity/implementation.md:891`)
  - Issue: the p01 disposition defers "duplicate helpers/warnings, case normalization, repeated transcript reads and lease/replay doc details" as follow-up after the feature stack, but no backlog item under `.oat/repo/pjm/backlog/` records them, and `implementation.md:577` states there are no deferred Medium or Minor findings awaiting disposition. Once the project archives, the follow-up is only discoverable in archived project prose.
  - Suggestion: capture one backlog item for the deferred maintainability/performance follow-ups (together with any Minor findings above that are deferred) and reword the line-577 statement to reference it.
