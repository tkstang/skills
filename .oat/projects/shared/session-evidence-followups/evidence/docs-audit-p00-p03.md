That is false for the paired structured-capture path: the implementation writes the Markdown first (`src/skills/session-export-transcript/src/session-export-transcript.ts:1530-1531`), then attempts the atomic activity JSON write, and on that failure explicitly reports `ACTIVITY_OUTPUT_WRITE_FAILED after narrative output was written to ...` (`src/skills/session-export-transcript/src/session-export-transcript.ts:1556-1565`). The authored user guide already states the correct boundary: the two files are not a filesystem transaction (`documentation/docs/user-guide/skills/session-export-transcript.md:177-183`).

Recommended narrow edit: change the canonical skill's exit-1 guidance to tell the agent to surface the exact error and note that a structured activity-output failure can leave the paired Markdown at the path named in the error. Align the complete-capture paragraph with the user guide's explicit non-transaction statement. Because this changes canonical `src/skills/session-export-transcript/`, apply the repository's normal skill-version, changelog, and generated-output rules during the later documentation pass.

Confidence: high. This is a direct contradiction between shipped instructions and an intentional implementation branch, not a speculative failure mode.
