## Findings

### Critical

- **Codex exact-all accepts conflicting cwd evidence** (`src/transcript/core/runtimes.ts:1174`)
  - Issue: `extractMetaFromRecords('codex', ...)` records only the first non-empty top-level or payload cwd and exits as soon as it also has a session ID (`src/transcript/core/runtimes.ts:1184`). The exact-all caller then trusts that result; its all-record cwd validation is Claude-only (`src/transcript/session-observer/lib/locate.ts:492`). A bounded transcript whose first record names the requested worktree and whose later record names a different worktree is therefore returned as an exact candidate. An independent generated-runtime reproduction returned one Codex candidate for that conflicting transcript instead of failing closed. This can expose the wrong session to selection and later mutation.
  - Fix: Validate every recognized top-level and payload Codex cwd in the bounded metadata prefix. Require each cwd to be a non-empty absolute path and require all observed values to agree; malformed or conflicting evidence must raise the existing path-free incomplete reason. Add exact-all tests for late top-level and payload cwd conflicts within the 128-record prefix and assert that no candidate is returned.
  - Requirement: FR1 (P0 exact-worktree discovery), NFR1 (P0 fail-closed inspection), NFR3 (P0 fail-closed security).

### Medium

- **A complete 128-record prefix with a trailing newline is falsely incomplete** (`src/transcript/core/runtimes.ts:846`)
  - Issue: After accepting record 128, `parseBoundedLines` marks the prefix incomplete whenever that record ended at a newline because `isFinalFragment` is false, even when the newline is the final byte and the complete file fit in the read buffer (`src/transcript/core/runtimes.ts:847`). An independent generated-runtime reproduction showed exact-all rejecting exactly 128 valid metadata records plus a trailing newline with `DISCOVERY_TRANSCRIPT_INCOMPLETE`. The same complete data without the conventional trailing newline is accepted. This is fail-closed and does not admit unsafe evidence, but it creates a deterministic availability failure at the supported record boundary.
  - Fix: Distinguish a newline terminator at the end of the buffer from data following the record cap. Add cases proving that exactly 128 records succeed both with and without a final newline, while a 129th record and byte-truncated prefixes remain incomplete.
  - Requirement: FR1 (complete exact set), NFR5 (bounded resource behavior).

- **Newline-bearing Git evidence cannot round-trip through the frozen schemas** (`src/transcript/coding-session-handoff/types.ts:636`)
  - Issue: The strict NUL-delimited porcelain parser correctly preserves a legal newline in a registered worktree path (`src/transcript/coding-session-handoff/git-target.ts:165`), and `inspectWorktree` returns that path. However, `parseGitWorktreeEvidence` sends every path field through the generic string validator, which rejects all code points below U+0020 (`src/transcript/coding-session-handoff/types.ts:361`). `parseSessionCandidate` applies the same validator to `recordedCwd` (`src/transcript/coding-session-handoff/types.ts:503`). An independent parser reproduction rejected produced newline-bearing evidence as `git-requested-path`, so the p02 producer and frozen consumer schema disagree for a path the Git parser explicitly supports.
  - Fix: Introduce a path-specific validator that accepts legal path characters while still rejecting NUL, or define and use a lossless encoded path representation. Keep display escaping separate from evidence validation. Add producer-to-parser round-trip tests for newline-bearing Git evidence and session candidates.
  - Requirement: FR4 (P0 Git safety evidence), FR1 (exact-worktree candidate schema), NFR3 (fail-closed input validation).
